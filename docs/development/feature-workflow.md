# Feature development workflow

This is the default lifecycle for KELIOS features and significant corrections. [AGENTS.md](../../AGENTS.md) governs ownership, Git safety and documentation lifecycle; [Architecture](../../ARCHITECTURE.md), [Domain](../../DOMAIN.md) and the active Plan own their respective contracts. Explicit task-specific limits take precedence. The operator alone grants human acceptance.

1. **Analyze (Plan Mode).** Inspect the current code, tests, contracts, active Plan, branch and worktrees. Separate verified facts, assumptions, product decisions and risks. Identify reusable interfaces and affected resources. Do not edit application code.
2. **Document and freeze.** Update the owning Plan and normative documentation where behavior changes. Record desired behavior, superseded decisions, stage boundaries, exclusions, verification and acceptance criteria. Human Plan approval and authorization to execute are distinct; do not implement from an unreviewed proposal.
3. **Implement, verify and commit stages.** In the isolated feature worktree, make each approved stage coherent and independently verifiable. Add focused regression coverage, run applicable checks, compare the result to the Plan, and record exact evidence and limitations. Approval of both the Plan and its execution is standing permission for scoped stage commits after verification. Inspect staged content and exclude secrets, generated backups and unrelated files. Material scope changes or unresolved safety risks return to planning.
4. **Update the local acceptance instance.** First establish its deployment owner and saved data/volume identity. Use the clean-checkout `./kelios update` for a CLI-managed instance, with the [operator backup procedure](../operations/backup-restore.md) where applicable. For a separately owned manual Compose instance, use only a verified owner-compatible update path and record exact impact. Preserve configuration, secrets, database and operator data. Verify running revision, service health and HTTPS routing. Local startup does not establish human acceptance. Production deployment requires separate authorization.
5. **Review and correct.** Return to a read-only Plan Mode review of the implementation, UI, contracts, Tenant boundary, test evidence and local observations. Classify accepted behavior, defects, documentation mismatches, scope changes and unresolved decisions. Plan and authorize bounded corrections; then verify, commit, update local and review again. Keep `Review: pending human acceptance` until the operator explicitly accepts the complete feature and its limitations.
6. **Push and open a PR.** After complete explicit HUMAN ACCEPTED status, passing required checks, synchronized documentation and a reviewed clean branch/commit manifest, verify remote `main`, push the feature branch and create a PR targeting `main`. The accepted-feature status is standing push/PR authorization; explicit stop conditions and branch protection still apply. Report PR/check status. Never merge automatically; merge needs separate explicit human authorization. Rebase, reset, force-push, production deployment and destructive data operations also need separate authorization.

Automated tests, a local installation and an agent's assessment are evidence, not operator acceptance. A Plan or work gate must truthfully state its current lifecycle status; historical acceptance remains dated when later revisions open.
