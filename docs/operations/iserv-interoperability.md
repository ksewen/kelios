Status: **Pending manual verification.** A test IServ environment is available. ## Prerequisites and provider configuration

Use a real Tenant IServ installation, an IServ administrator, a KELIOS ACTIVE GLOBAL ADMIN, test users with mapped and unmapped group/role memberships, trusted HTTPS/DNS, and backend network access to the provider. Record deployed IServ version as an observation: official documentation does not specify a minimum version for this contract.

Primary references: [IServ SSO configuration and claims](https://doku.iserv.de/manage/system/sso/) and [IServ developer UserInfo example](https://doku.iserv.de/development/oauth/). Configure a client under IServ Administration → System → Single-Sign-On, enable authorization-code grant, register the exact KELIOS callback URI, and allow required scopes. Users need the provider's documented OAuth-use permission. Verify consent/client restrictions rather than assuming access is granted.

KELIOS requests `openid profile`, adding `iserv:groups` when group rules exist and `iserv:roles` when role rules exist. It does not request WebUntis scopes. KELIOS requires S256 PKCE and validates nonce/state; confirm the installed provider accepts the flow. Do not downgrade validation if configuration/version is incompatible.

For the configured trusted KELIOS public origin `https://kelios.example` and Tenant UUID `<tenantId>`, register exactly:

```text
https://kelios.example/api/v1/auth/oidc/<tenantId>/callback
```

Replace origin/Tenant using actual deployment values. `KELIOS_AUTH_PUBLIC_ORIGIN` must match the external HTTPS origin; redirects are not inferred from browser Host/forwarded headers. Backend discovery uses the configured issuer and its Discovery document, not copied WebUntis endpoint examples. Confirm the discovered issuer matches exactly, with working authorization/token/UserInfo/JWKS endpoints and appropriate client authentication. Production egress/TLS trust configuration must allow the real provider; explicitly allow private/provider-secondary hosts where required. Never disable TLS validation or use an arbitrary redirect.

## KELIOS configuration and group/role selection

1. Sign in as ACTIVE GLOBAL ADMIN, open **iServ**, then use **Add or configure iServ** to select the Tenant. If no Tenant exists, use **Create Tenant** first. ACTIVE TENANT ADMIN may only read the signed-own sanitized configuration and never uses the Tenant collection as a selector. Administrator credentials and mounted signing/encryption keys must already be configured; see [authentication operations](authentication.md).
2. Identify the intended IServ Gruppe account `act` from administrator-controlled UserInfo inspection with `iserv:groups`, and/or the IServ Rolle `displayName` with `iserv:roles`. Group `name` is display-only; group `id` and role `uuid`/deprecated `id` are opaque and never used for authorization. The documented group and role responses are lists; the controlled test provider also returned group records keyed by opaque `id`. Do not copy complete personal payloads into project evidence.
3. As ACTIVE GLOBAL ADMIN, use the single Connector rule table to choose Gruppe or Rolle, enter the exact case-sensitive `act` or `displayName`, and map it to KELIOS USER or ADMIN. The API carries separate `groupMappings` and `roleMappings` lists, for example `{"groupMappings":[{"act":"school.users","role":"USER"}],"roleMappings":[{"displayName":"School administrator","role":"ADMIN"}]}` within the full PUT body. Allow `iserv:roles` on the dedicated IServ Client when role rules are used. Any valid rule match permits login; any matched ADMIN wins at first creation. No match returns 403. New users remain PENDING; only GLOBAL ADMIN can approve a mapped ADMIN. Subsequent logins require a current match but do not change stored KELIOS role. An omitted `roleMappings` field retains existing role rules on update, while `[]` clears them; the UI submits both lists.
4. As GLOBAL ADMIN, create the Connector with the exact issuer, client ID and mappings; omit the secret and keep `enabled=false`. On creation version is null; subsequent updates use the GET response version. Then use **Geheimnis festlegen** (or `PUT /api/v1/tenants/{id}/oidc/secret` with a nonblank `clientSecret` and current `version`) to set the secret separately. Setting the secret does not enable the Connector; review the sanitized details and explicitly switch Aktiviert to Ja. Existing API callers may still supply a secret in the full configuration PUT. Submit secrets only through a private HTTPS administration client/input, never a shell argument or checked-in example/evidence.
5. Verify sanitized `GET` shows the correct Tenant/issuer/client ID, `secretConfigured=true` after the separate secret step, mappings, version and derived `callbackUri`, but no client secret/ciphertext. An incomplete Connector reports `secretConfigured=false`, stays disabled and is absent from the login directory. Register the exact callback on IServ. Existing UUID allowlist rows are retained by the schema migration as textual accounts with USER role; a GLOBAL ADMIN must replace them with the actual `act` values before login can match.
6. Open `/login/tenant/<tenantId>` or enter the Tenant UUID in the authentication form. Start uses the dynamically loaded database configuration. Observe redirect to the discovered provider endpoint; never capture authorization codes or full callback URLs in evidence.

If the administration UI does not expose `act`, use an administrator-controlled OIDC inspection client: obtain Discovery from the exact issuer, perform authorization-code login with `openid profile iserv:groups`, nonce and S256 PKCE for a representative group member, exchange the code privately, and call the discovered UserInfo endpoint with that request-local Bearer token. Copy only the intended `act` into KELIOS configuration. Keep credentials/codes/tokens/payloads private and discard them after inspection; use a separately registered inspection redirect if the tool requires one. This uses the documented UserInfo contract, not an invented groups API. KELIOS deliberately does not expose raw provider memberships on a failed login. Exact UI/tool availability is a later setup observation.

## Positive, negative and account lifecycle tests

Use an isolated browser profile for each positive/negative account, or explicitly sign out of KELIOS and select the intended IServ account. KELIOS logout does not terminate provider SSO. A failed new login issues no new KELIOS tokens but does not revoke a previously issued Refresh JWT; do not mistake an older session for a successful negative test.

| Step | Action | Required KELIOS result / provider observation |
|---|---|---|
| Allowed first login | Authenticate an unused identity belonging to a mapped `act` group. | Successful callback; a single User with TENANT scope, this Tenant, mapped USER or ADMIN role, PENDING status. Pending contact-administrator message; no business/admin data. Verify actual claim shape and matching UserInfo subject privately as provider observations. |
| Negative login | Authenticate a different user outside every allowed group. | Denied callback; no new User/external mapping or issued KELIOS refresh cookie. Confirm the denied group condition, without recording the full membership payload. |
| Approval | GLOBAL ADMIN approves `/api/v1/users/<id>/approve`, or same-Tenant ADMIN approves an ordinary USER. | ACTIVE. Refresh or subsequent OIDC login yields ACTIVE access; TENANT ADMIN cannot grant ADMIN. |
| Identity continuity | Repeat login for the same account; optionally change its display name/email in IServ and repeat. | Same KELIOS User UUID from the same issuer/subject, no duplicate. Display/email are not identity keys. Record continuity outcome; keep subject/user values private or pseudonymized. |
| Disable | Authorized administrator calls `/api/v1/users/<id>/disable`. | New refresh rejected; OIDC login issues no new tokens. Previously issued ACTIVE Access JWT remains valid until its normal approximately 15-minute expiry. |
| Later group removal | For another approved ACTIVE account, remove provider membership or remove its `act` from the KELIOS mappings. | A new OIDC login is denied. Existing KELIOS User remains ACTIVE; existing refresh still works until absolute expiry, with no provider lookup. No automatic sync/disable/revocation. Manually DISABLE to deny future refresh. |
| Empty mappings / configuration failure | In a controlled test, remove all mappings; separately check unavailable/misconfigured provider behavior. | Fail closed; no new provisioning/tokens. Restore configuration with the current version before retesting. |

PENDING can authenticate/refresh and inspect minimal self status only. Access-token permissions/status are snapshots; refresh reloads current KELIOS User. Logout discards browser access and clears refresh cookie, without server revocation or a claim to log out the IServ SSO session. No forced first-login password change applies to GLOBAL bootstrap/recovery; that is independent of Tenant OIDC.

## Troubleshooting observations

- **Discovery:** compare configured and returned issuer exactly; verify HTTPS chain, backend DNS/egress, timeouts, supported signing algorithm, and discovered endpoints. Check installed version/configuration; do not replace Discovery with hard-coded paths.
- **Private gateway DNS:** `OIDC stage=discovery transport=UnknownHostException` can mean DNS failure or the provider HTTP policy rejected a private DNS result. Resolve the issuer hostname inside the backend container. If it resolves to an operator-approved private iServ gateway, use the deployment CLI's persisted `TRUSTED_PROVIDER_HOSTS` setting for that exact hostname, then run `start` and retry. Do not whitelist an address range or disable TLS/issuer validation; see [deployment configuration](deployment.md#configuration-and-tls).
- **Issuer input:** a single terminal `/` in a Global Admin configuration write is calibrated through live Discovery and stored as the returned exact issuer. Other mismatches or an unreachable provider reject the write without changing the current configuration. Login still compares the exact stored issuer with Discovery and ID Token `iss`.
- **Redirect:** compare GET `callbackUri`, registered provider URI and externally reachable origin byte-for-byte. Check scheme, port, Tenant path and reverse-proxy routing; do not trust arbitrary forwarded headers.
- **Scopes/permissions:** confirm `openid profile` and the scopes required by configured rules (`iserv:groups`, `iserv:roles`, or both) are requested/permitted and the user's OAuth permission/consent is valid. Do not add undocumented scopes; role displayName grants authority only through an explicit Connector rule.
- **State/nonce/PKCE:** start a fresh browser flow; confirm Secure/Lax flow-cookie delivery on the GET callback and S256 support. Verify all checks without publishing verifier/state/nonce/code values.
- **UserInfo:** confirm endpoint/token authorization succeeds and `sub` equals the validated ID-token subject. A mismatch denies login; do not repair it by username/email matching.
- **Missing/malformed groups:** check for a documented list or the observed object-of-records shape with valid `id` and `act` strings. Missing or malformed group information grants no group authority; a valid mapped role can still permit login. Unavailable UserInfo always denies. Capture only sanitized shape/outcome.
- **Group mismatch:** compare exact `act` values with Connector mappings privately; `name` and opaque `id` do not grant authority; role `displayName` can grant only through an explicit role mapping. Record only whether a mapping matched.
- **Cookies/refresh:** use same-origin HTTPS, trusted Origin and the CSRF exchange; CORS is disabled. Existing HTTP technical smoke is not an authenticated browser deployment. Check certificate trust, cookie path/flags and browser clock without weakening validation.
- **Configuration change:** a flow started before a provider-version change is rejected; restart login. Disabled/missing provider config fails closed. Errors/logs must not reveal codes/tokens/secrets.

For a controlled local interoperability retry, `KELIOS_OIDC_DIAGNOSTICS_LEVEL=DEBUG ./kelios --state-dir <saved-state> start` enables only the dedicated OIDC diagnostic logger. It reports fixed stage/reason codes, provider HTTP status, bounded sanitized UserInfo field names/types, group/role item shape/count and source-specific mapping intersections. It never prints raw claims, identifiers, credentials, tokens, cookies or full URLs. Use a fresh browser login, note the time and inspect only the relevant backend log lines. Run `./kelios --state-dir <saved-state> start` without that variable immediately afterward, then verify backend health and that the diagnostic level is INFO. The switch defaults to INFO and is not saved in installation state; do not enable broad Spring HTTP wire logging or provider-payload logging.
