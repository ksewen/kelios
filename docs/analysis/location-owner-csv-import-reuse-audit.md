## Architectural recommendations, not approved implementation

**CSV configuration UI reuse:** Follow the accepted Asset importer's encoding, delimiter, invalidation, parse-error and source-preview interaction where applicable. The Place control requires an explicit header yes/no choice and a concrete delimiter rather than AUTO. Implement it locally; no shared component extraction is justified solely by this one-column import. This decision is independent of parser reuse.

**CSV parser reuse decision:** The approved source has one name column, so a bounded Place-local browser parser is the smaller implementation. Use browser decoding for the approved encodings and handle quoted fields, doubled quotes, record/line numbers and bounds; reject malformed input or extra columns before execution. Direct use of the Asset parse-preview route is unsuitable for TENANT ADMIN. A shared backend endpoint or extraction would add transport/security work and Asset coupling without serving this narrow contract. Do not change Asset AUTO delimiter detection solely for this feature. If the source contract later expands, reassess backend reuse under a revised and separately authorized plan.

**Place execution:** Use existing JSON Create APIs per row, with one fixed target Tenant and `{name, note: null}`. This supports independent transactions and partial success without a new bulk API. Preserve row identity and backend error codes. Duplicate names are permitted; no duplicate precheck or overwrite follows from the Asset warning logic.

## Later CSV settings parity decision and implementation audit (2026-10-31)

The older recommendations above describe the planning baseline, before the human authorized implementation and then the settings-parity correction. They are retained as dated evidence. The [owning Plan](../plans/location-owner-csv-import.md#csv-settings-parity-correction-authorized-2026-10-31) records the active decision and verification. The later decision supersedes the older no-`AUTO` UI recommendation; it does not alter the one-column source contract or Asset behavior.

**Verified implementation difference and cause:** Accepted Asset UI `frontend/src/features/inventory/AssetCsvImport.tsx` uses `AUTO` first and by default for both encoding and delimiter. Before correction, the shared Location/Owner `PlaceCsvImport.tsx` omitted both `AUTO` choices, defaulting to UTF-8 and semicolon; its local `place-csv.ts` took only an explicit delimiter. That matched the earlier Place plan but failed the subsequently confirmed settings-parity requirement. Both Place collection entry points use the same component in `frontend/src/features/inventory/pages.tsx`. Asset automatic encoding is strict UTF-8 with optional BOM in backend `AssetCsvParser.java`; its separate automatic delimiter mechanism checks semicolon/comma/tab and requires a multi-column parse. Asset parse-preview remains Asset-scoped and GLOBAL ADMIN-only, so direct reuse for TENANT ADMIN would require a new authorization-safe backend interface.

**Architectural decision:** Keep the Place parser local and execution independent. `PlaceCsvImport.tsx` now uses the accepted `csv.*` labels, option order and defaults, with Place-specific guidance. `place-csv.ts` decodes `AUTO` as strict UTF-8 and rejects explicit legacy selection with a UTF-8 BOM. For delimiter `AUTO`, it parses semicolon, comma and tab interpretations and accepts only a common valid single-column result; it reports possible extra columns with their source line before any POST. An explicit delimiter determines structure, leaving other punctuation as name data. This is validation of a delimiter-free one-column file, whereas Asset's `AUTO` detects a delimiter in multi-column input. The difference is required by the respective source contracts. No Asset parser change, new endpoint, dependency, extraction or general CSV framework was needed.

**Regression scope and limits:** `frontend/src/features/inventory/place-csv.test.ts` and `frontend/tests/place-csv-import.spec.ts` cover the new modes, invalid bytes/BOM, headed/headerless one-column files, ambiguity, explicit resolution and no writes after structural failure. The Plan records exact commands and counts, including manual Place Create and Asset CSV regressions. Browser HTTP was mocked; no live database write occurred. A later request updated the local 8443 frontend image; the Plan records that deployment and its health checks. The remaining user-visible constraint is that an unquoted comma, semicolon or tab in a name is ambiguous in `AUTO`; choose a delimiter explicitly or quote that name. Review remains pending human acceptance; this audit does not claim it.

## Later Place wizard alignment audit (2026-10-31)

The human authorized a three-step wizard in the existing Location/Owner collection dialog. `PlaceCsvImport.tsx` previously cleared parsed rows after any setting change and parsed only on Check file; that caused the manual reload requirement. `AssetCsvImport.tsx` supplies the step indicator, focused headings, Back/Next placement and result conventions. Its file and header changes start parsing, whereas encoding and delimiter changes invalidate the preview until Check file is clicked. The later Place requirement calls for automatic reparsing on every file/configuration change without modifying Asset.

The Place UI now follows those wizard conventions with local `File` and settings state, automatic parsing guarded by a generation and a matching configuration snapshot, and a reviewed Tenant/row snapshot for execution. This changes only `PlaceCsvImport.tsx`, Place-specific English/German labels and its browser tests; the one-column parser, Tenant-scoped Create API and Asset code remain separate. The owning [Plan](../plans/location-owner-csv-import.md#place-wizard-alignment-authorized-2026-10-31) records the exact flow, test results and limits. This audit remains supporting evidence rather than an alternate UI contract. Human acceptance is pending.
