## Lock and transaction review

**CONFIRMED:** OIDC PUT, DELETE and final provisioning acquire the Tenant parent before the configuration row (`TenantService.lock`, `OidcConfigurationService.lockTenant/locked`). Final provisioning then acquires external identity/User state. It does not hold database locks during discovery/token/UserInfo network requests. DELETE cannot commit ahead of a provisioner holding that parent lock; a provisioner arriving after committed deletion must load current configuration or fail. Existing User administration does not acquire configuration locks after holding a User lock, so no reverse OIDC/User cycle was found.

**CONFIRMED:** Administrator recovery-sensitive paths acquire the recovery guard before the managed User lock (`AuthenticationService.bootstrap/approve/role/resetCredential/email`). Login reads User then credential under share locks; credential mutations lock User before credential. Ordinary User disable/role changes and final JIT User status validation serialize on the User row. These conclusions apply to supported writers, not arbitrary direct SQL.

**INFERRED concrete concurrency debt:** Product edit/publish obtains Product UPDATE before Category/Manufacturer SHARE (`ProductOperations.writable`, `CatalogService.editProduct/publish`). Category/Manufacturer Merge obtains label UPDATE before dependent Product UPDATE (`CatalogService.lockMerge/redirectProducts`). Concurrent edit of an unreferenced Product and Merge of its current Category can therefore form a wait cycle: edit holds Product and waits for Category; Merge holds Category and waits for Product. PostgreSQL would abort a participant, preserving transaction rollback, but this may surface as an avoidable command failure. This audit did not reproduce that schedule; it is not claimed as an observed data-loss/security defect. Smallest next gate: deterministic isolated PostgreSQL race verification, then review a resource-specific common lock order if confirmed. Do not add blanket retries or a generic mutation engine. Accepted steps are not reopened automatically.

V2 ownership/check/composite reference constraints, V4 external `(issuer, subject)` identity and scope-consistent credential/mapping FKs, V5 captured audit ownership, V7 non-null business metadata/reserved-actor exclusion/Place notes, and V8 canonical Email uniqueness form the accepted target schema. Configuration singleton PK and child FK already support physical deletion; no new schema is necessary.

**CONFIRMED:** OpenAPI administration descriptions match GA/TA corrected Tenant/OIDC policy, versioned physical DELETE, Email commands, bounded User Page/detail and Audit criteria. HTTP mapping in `IdentityAdminController`, resource controllers and security request matchers agrees with that surface. OIDC DELETE returns 200/empty body and requires `version`; stale version conflicts, repeated missing is 404. Audit optional inclusive offset/UTC bounds and microsecond validation match DTO/query/SQL. No new API discrepancy established in these inspected boundaries. This was a targeted source/API comparison, not a claim of exhaustive automated OpenAPI conformance.
