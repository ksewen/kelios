## 1. Goal, ownership, and boundaries

Make deployment an operator operation rather than a procedure tied to one developer's checkout. Linux server installation is the first-class target. An operator supplies stable deployment intent; the CLI handles paths, validation, temporary work, fresh secret initialization, and routine lifecycle without silently replacing persistent state. The [Architecture](../../ARCHITECTURE.md) retains the separate frontend/backend images, PostgreSQL, Flyway, runtime branding, and same-origin HTTPS contract. [Domain](../../DOMAIN.md) retains administrator recovery and authorization policy. This Plan owns deployment tooling and operator workflow only.

Gate 0 uses branch `feat/deployment-workflow-v2` in an isolated worktree based on `main` commit `e4ec59a59797c3ec417b85a3cd3f2241cc078614`. The original worktree is `feature/asset-csv-import-export` at `d038be9023cb6fefffc4209abb6e49be69bbad7b`, with dirty CSV-related work. No CSV branch content is a dependency or part of this Plan. Do not change inventory, Assets, Catalog, Places, Users, authorization, CSV import/export, unrelated frontend UI, or backend business services. A narrowly required application deployment-contract change must first be justified in this Plan and separately authorized.

**Non-goals:** a release-bundle or published-image distribution system, Docker/Compose installation, rootless Docker/Podman, multiple proxy drivers, ACME/public certificate issuance, automatic secret rotation, v1 migration, a general backup/restore CLI, or an application-schema change. Do not add abstractions for these deferred capabilities.

## 2. Confirmed current-state audit

The repository-level POSIX [CLI](../../kelios) derives `ROOT` from its own script path but puts `STATE` and the lock under that source checkout (`kelios:8–10`). Its seven commands are install, start, stop, status, config, uninstall, and recover-admin (`kelios:25–28`). It has interactive-only install/config/recovery, Docker/Compose/OpenSSL checks that conflate daemon outage and access denial (`kelios:31–53`), and no explicit host privilege model. There is no sudo or root requirement in the CLI; Docker socket access is implicit and high privilege. Shell syntax is POSIX-oriented, but current operator instructions and verification tools reflect one macOS host.

`deploy/compose.yaml` builds distinct backend/frontend images from relative build contexts. `compose.postgres.yaml` adds PostgreSQL 17 with a named `postgres-data` volume; external-database mode omits that overlay. `compose.auth.yaml` mounts authentication keys and TLS material and adds HTTPS to the unprivileged frontend Nginx container. Nginx serves the SPA/runtime branding and proxies `/api/` to backend. The backend applies Flyway migrations on startup. Docker Engine, Compose v2, BuildKit, OpenSSL, daemon access, and available host ports are required; Docker Desktop is mentioned in the guide as an example for external-database host addressing, but is not used by the CLI. The image and architecture support matrix has not been proven on Linux. Frontend/backend images remain independent; the CLI currently uses fixed `phase0` image names from Compose rather than a release/update identity.

Fresh install generates a managed DB password and RSA 3072 signing/AES-256 encryption keys, or copies an operator-supplied authentication-key set (`kelios:248–284`). Backend recovery receives a private mounted password file, and backend policy controls zero-usable-admin creation (`kelios:203–220`; Domain §2). The CLI validates and copies operator-supplied TLS PEM files; it does not generate certificates (`kelios:181–189`, `235–247`). The [guide](../operations/local-deployment.md) manually creates a 30-day self-signed localhost certificate with OpenSSL and asks the operator to enter its paths (`local-deployment.md:26–45`). A 30-day default is unsuitable for the intended private-network workflow.

## 3. V2 operator contract — proposed, pending review

**Source and state.** Initially support a clean source checkout containing `kelios`, `deploy/`, `frontend/`, and `backend/`. The CLI resolves those from its own path and takes an optional `--state-dir`; the default instance root is `${XDG_DATA_HOME:-$HOME/.local/share}/kelios/default`. The source is replaceable. Within the instance root, keep validated non-secret configuration, private secrets (DB password, auth keys, TLS key), public branding, and generated deployment metadata distinct. PostgreSQL data stays in its named Docker volume; external PostgreSQL stays externally owned. Logs belong to Docker and private diagnostics, not the source tree. Generated Compose inputs are disposable, regenerated from validated state, and never become the operator's editable config. Use one instance initially; no instance manager.

**Workspace and failure.** Create a `0700` OS-managed temporary directory with `mktemp -d`; use `umask 077`. Clean it on normal exit, expected error, catchable signal, and handled unexpected failure. Write only sanitized diagnostics to a private persistent diagnostics directory when troubleshooting requires retention; disclose its location. Do not retain rendered secrets, recovery passwords, or raw provider claims. A crash that cannot run a trap may leave an OS temp directory; doctor identifies only KELIOS-owned stale work for operator inspection, never broad-cleans `/tmp`.

**Secrets and certificate.** Fresh install generates DB password and auth RSA/AES keys by default, or imports validated operator-provided key files. Existing instance state cannot be overwritten by install, update, start, restart, or deploy. Key loss blocks use of an existing encrypted database; regeneration is never recovery. Rotation is outside v2. Add optional `kelios certificate init` before install. It collects the intended DNS hostname or IP address, persists that non-secret identity, and generates a self-signed private certificate/key atomically in instance state. Use the primary identity as a SAN; for `localhost`, also include loopback IP. Default validity is **730 days**; report expiry and trust implications. No separate CA/root artifact or public ACME. Rerun refuses existing material. `kelios certificate replace` is the explicit, confirmed replacement path, with a preflight check that the new certificate covers the persisted hostname; replacement never occurs during install/update/restart. When provisioning was skipped, install accepts and imports validated operator-supplied PEM files. Private certificates are for local/explicitly trusted private networks; public service uses an operator-supplied trusted certificate. External TLS termination is a future publishing mode, not an install fallback in the initial profile.

**Privileges and Docker.** Run as an ordinary user. Docker Engine and `docker compose` v2 with working daemon access are prerequisites; KELIOS does not install or start them or silently alter host security. `doctor` distinguishes missing executable/plugin, stopped daemon, and denied socket. Docker group membership is effectively high-privilege host access, not a harmless permission fix. An explicit `kelios host prepare docker-access` may offer a narrowly scoped supported group change with targeted sudo after displaying the exact effect and requiring approval; hosts already configured are unchanged. The normal containerized Nginx path uses a non-privileged host port, so no root CLI, systemd, or privileged-port change is required. Pure rootless Docker/Podman is unsupported in v2: networking, volumes, mount ownership, and compatibility would need a separate tested contract. Do not wrap all Docker calls in sudo or change `$HOME` through root execution.

| Privilege model | Security and ownership | Docker, proxy, systemd, unattended/debugging outcome |
|---|---|---|
| Ordinary user with targeted sudo — **selected** | State stays owned by the operator. Only a separately confirmed host-access operation may elevate; Docker access itself is high privilege. | Existing Docker/Compose is required. Containerized Nginx uses a high host port; no systemd/package setup. Normal commands work unattended once access and config exist. |
| Require a sudo-capable account for every operation | Unnecessary sudo eligibility expands the host credential requirement and confuses whether generated files are root-owned. | Does not remove the Docker-access prerequisite; adds friction to unattended and debugging flows. No current systemd or host Nginx need justifies it. |
| Run the whole CLI as root | Broad host privileges; root-owned state and changed `HOME` complicate later operator use and upgrades. | Could reach the Docker socket and privileged ports but increases the impact of every CLI error. Rejected. |
| Pure unprivileged/rootless runtime | Depends on preconfigured rootless Docker/Podman and different networking, mounts, and volume ownership. | Practical only as a separate tested profile; no present implementation or support claim. |

**Publishing.** Nginx is the existing frontend runtime and proxy implementation, not a business or backend architecture requirement. Initial v2 uses containerized Nginx for same-origin HTTPS, `/api/` proxying, runtime branding, and callback-query log redaction. Keep the profile boundary at origin/routing/TLS mounts so a future external proxy can satisfy the same contract; do not add a generic driver hierarchy now. Certificate issuance and renewal are operator responsibilities except for the optional private certificate command.

**Configuration and commands.** A validated non-secret instance config is the stable interface. Interactive prompts fill missing install settings; `--config` and file-based secret inputs support noninteractive use. Do not put secret values in arguments or ordinary environment variables. Planned commands: `certificate init|replace`, `doctor`, `host prepare docker-access`, `install`, `update`, `start`, `stop`, `restart`, `status`, `logs`, `config`, `recover-admin`, and `uninstall`. No separate `deploy` alias until it has a distinct purpose. `install` is fresh-only; an incomplete prepared install resumes through an explicit supported recovery path without new secrets. `update` takes the invoking clean checkout as the target release, builds versioned independent images, then applies them only after preflight/build success. `start`/`restart` reapply saved config without build, secret generation, or bootstrap. `stop` retains all state. `status` and bounded `logs` are read-only. `config` stages and validates changes. `recover-admin` retains backend zero-usable-admin authority. `uninstall` removes runtime only by default; permanent managed-volume removal requires exact typed confirmation and ownership checks. Commands are rerunnable where their purpose permits; install never means reset.

| Command | Prerequisite, privilege, persistent effect, and rerun/failure rule |
|---|---|
| `certificate init` / `replace` | OpenSSL and writable private state; ordinary user. Init creates identity/key/cert once and refuses a rerun; replace requires explicit confirmation and atomically keeps old material on failure. |
| `doctor` | Available before install; ordinary user, read-only. Reports prerequisites and state without trying to repair the host. Safe to rerun. |
| `host prepare docker-access` | Installed Docker and sudo-capable operator; displays the proposed security-sensitive host change and obtains explicit approval. Idempotent when access already works; a group change may require a new login. |
| `install` | Clean source, Docker/Compose, valid config/TLS, absent instance; ordinary user. Creates state, secrets, runtime and guarded initial admin. Existing or prepared state never gets fresh secrets; report supported recovery after partial failure. |
| `update` | Existing healthy/known instance, clean target source, successful preflight; ordinary user. Builds new versioned images and switches runtime, retaining database, secrets, cert and prior image. Retry targets the same release; report committed-migration limits. |
| `start` / `restart` / `stop` | Existing instance; ordinary user. Start/restart apply saved config and are repeatable; stop is repeatable. None alter persistent data or generate secrets. A failed start leaves state for diagnosis. |
| `status` / `logs` | Existing or absent instance; ordinary user, read-only. Status describes service health; logs are bounded and redacted at the auth callback boundary. Repeatable. |
| `config` | Existing instance; ordinary user. Validate and atomically save supported non-secret settings; leave old config intact on failure. Runtime-affecting changes apply on start. |
| `recover-admin` | Existing runtime/database and private Email/password input; ordinary user. Backend permits creation only with zero usable Global admins; refusal leaves account state unchanged. Never an automatic install/update side effect after initialization. |
| `uninstall` | Existing owned instance; ordinary user. Default removes runtime only and is repeatable. Managed database deletion requires a separate exact confirmation; external database is never dropped. |

**Preflight, updates, and data safety.** Before expensive work, validate supported OS/architecture, required executables and versions, Docker/Compose/daemon/access, configured port availability, path ownership/permissions, practical free-space estimate, instance state, Compose rendering, volume identity, required secrets, TLS hostname/expiry, and external DB reachability as applicable. Report problem, reason, and corrective action. Update/redeploy/restart/frontend rebuild cannot delete or recreate PostgreSQL data, uploads, keys, certificates, configuration, or backups. An initialized managed instance with a missing volume fails closed. A failed build leaves current runtime unchanged; a partial runtime switch retains persistent state and gives recovery instructions. Flyway may commit migrations before a later failure, so do not claim automatic DB rollback. Operators own production backups; v2 does not create a general backup/restore product. Verify preservation with disposable sentinel rows and an isolated recovery drill, and document the update backup prerequisite for real operation.

**Compatibility and prior installations.** Linux server AMD64 is the first supported production target only after Linux verification records the exact distro/runtime versions. Linux ARM64 and macOS development are expected compatible but unverified until separately tested. Legacy `docker-compose` and rootless runtimes are unsupported. The human confirmed no real v1 deployment requires migration: the only v1 installation is disposable local test state. V2 does not auto-adopt it, depend on it, or remove it; deprecate the old workflow only after v2 acceptance. Existing historical evidence remains intact.
