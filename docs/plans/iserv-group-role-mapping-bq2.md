## Scope and ownership

BQ1's controlled test proved that this IServ test environment returns `iserv:groups` as an object keyed by opaque non-UUID `id`; each value has `id`, readable group account `act`, and display label `name`. The official IServ documentation describes a list of objects and a UUID `id`; the observed test provider differs. The connector must accept both documented list and observed object forms, validate every entry, and fail closed on malformed or ambiguous groups. `act` is the exact, case-sensitive authorization key. `name` is descriptive only and is never an identity or permission key.

The Tenant OIDC singleton gains explicit group mappings from `act` to KELIOS `USER` or `ADMIN`. Any mapped group grants login eligibility; if both roles match, ADMIN wins only at first User creation. Every new OIDC User remains PENDING. A mapped ADMIN requires GLOBAL ADMIN approval because TENANT ADMIN cannot administer ADMIN users. Later OIDC logins still check membership in at least one configured group but never overwrite the stored KELIOS role/status. Refresh and already issued sessions retain the existing behavior. A missing/malformed group claim, duplicate/ambiguous account, or no mapped group denies login without provisioning.

The existing `tenant_oidc_allowed_group` UUID rows and local operator data must not be dropped. An additive migration evolves each old UUID to a textual `act` entry with USER role; Global Admin must explicitly replace those legacy values with actual IServ group account names. The observed login claim provides readable `act` values, and the Connector must configure those values rather than copied `id` fields. Do not infer a mapping from UUIDs or existing test values. Configuration write remains GLOBAL ADMIN only; TENANT ADMIN reads only its own sanitized configuration. Client secrets and provider claims remain outside administrative responses and Git.
