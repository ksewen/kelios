## Audited findings and accepted decisions

| Surface | Classification | Contract |
|---|---|---|
| Tenant columns and modal | Presentation plus creator projection | Tenant list already has creation time and creator UUID. Show Name, Created at, Created by; open from list in a lightweight dialog while retaining independently authorized deep-link detail. |
| Shared breadcrumb | Shared frontend correction | Use a semantic, accessible breadcrumb. User detail is Home > Users > authoritative display name; preserve contextual dashboard and User collection destinations. |
| User columns | Presentation plus safe API projection | User list lacks Email; show Name, Email, Role, Tenant, Status, Created at, Created by. Tenant users have no local Email. Existing server sort/filter limits remain. |
| Creator names | Domain/persistence/API change | For Tenant, User, Category, Manufacturer, Product, Asset, Location and Owner, `createdByDisplayName` is a **historical creation-time snapshot**, while `createdBy` remains authoritative identity. Store only a trusted label actually available in the creation transaction. Never infer a historical name from current Users, Audit history, a claim that is not trusted for this purpose or another record. Existing unknown snapshots remain nullable/unresolved; system/seed has its explicit label. Existing update-actor semantics stay separate. |
| User Edit | Atomic API/security change | Current Email and role routes are separate. One guarded Save must apply only changed eligible fields in one transaction; Name/profile and identity/scope remain read-only. |
| Role at creation | HUMAN-approved domain change | GLOBAL ADMIN may create GLOBAL ADMIN directly through one atomic creation Save; default remains USER, existing clients omitting role remain USER. TENANT ADMIN gains no creation path. |
| Activate/disable | Existing policy | Aktivieren means only PENDING approval. DISABLED reactivation remains undefined. |

For ordinary GLOBAL accounts, Passwort zurücksetzen edits only the password; the existing credential repair path may still require an explicit Email when no credential exists. Separate legacy Email/role endpoints remain supported. The existing User `displayName` editing decision stays pending.
