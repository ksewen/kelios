## Goal and boundary

Import multiple Location or Owner names from a CSV through the same creation semantics as the existing Standorte and Eigentümer forms. This is a small administrative convenience, not iServ integration, a data migration, or a general import framework. One import creates one resource kind in exactly one concrete Tenant. No timestamps, historical state, automatic reference matching, note mapping, deduplication, overwrite, or new business meaning are implied.

**Historical CSV source contract (approved 2026-10-31; superseded for the new revision):** Exactly one column containing a Location or Owner name. iServ is a possible source of names, not a required export format; no representative iServ file is needed. The settings UI requires an explicit choice of *header present* or *no header*. A headed file has exactly one header whose outer whitespace is stripped and whose value equals `name` case-insensitively; no other alias is accepted. A headerless file treats its first record as data. The former implementation rejected additional columns and offered no field mapping. The 2026-11-01 revision below replaces these source-format restrictions without changing the dated acceptance of the earlier implementation.

The historical baseline used the accepted Asset CSV encoding choices: strict UTF-8 by default with optional UTF-8 BOM, plus explicit Windows-1252 and ISO-8859-1 choices. It initially required a concrete delimiter: semicolon by default, with comma, tab and custom single-character options, and did not offer automatic delimiter detection. Later accepted corrections added AUTO settings; the mapping revision below defines the current target. Quoted fields, doubled quotes, CRLF/LF endings and the 5 MiB file / 5,000-row / 32 KiB-cell safety limits remain relevant.

## Confirmed domain, API, and UI contract

- `Location` and `Owner` are flat Tenant-owned resources. V2's `location` table has a non-null Tenant FK and a non-null, nonblank `name`; `owner` inherits its column constraints. V7 adds nullable `note` and server-owned creator/update metadata. Neither table has a unique constraint on `name`, so duplicate names are permitted and are not inherently invalid. See `backend/src/main/resources/db/migration/V2__domain_foundation.sql` and `V7__business_metadata_and_place_note.sql`.
- `PlaceModel.Command` and `PlaceService` require a nonblank name and strip surrounding whitespace. They normalize omitted, null, or blank note to null. `PlaceDtos.Command` requires textual `name`, accepts optional textual/null `note`, and rejects unknown fields. **Name alone is sufficient for both creates.** See `backend/src/main/java/com/github/ksewen/kelios/inventory/PlaceModel.java`, `backend/src/main/java/com/github/ksewen/kelios/inventory/PlaceService.java`, and `backend/src/main/java/com/github/ksewen/kelios/platform/security/PlaceDtos.java`; the public schema is `PlaceCommand` in `docs/api/openapi.yaml`.
- Existing `POST /api/v1/tenants/{tenant}/locations` and `/owners` return `201` with a created ID. `PlaceOperations.create` requires an active administrator, resolves the concrete Tenant, and delegates to the transactional create service and audit. GLOBAL ADMIN supplies an authorized concrete Tenant; TENANT ADMIN uses its signed Tenant, regardless of a supplied path Tenant. The importer will use these existing APIs, one POST per row; no backend creation change is required. See `PlaceController.java`, `PlaceOperations.java`, and `backend/src/test/java/com/github/ksewen/kelios/identity/auth/PlaceIT.java`.
- The current `Management` Create form requires name, offers optional note, and sends `{name, note: null}` when note is blank. In Global context it requires a Tenant choice; in a concrete Tenant context it displays a read-only target. Tenant principals derive their context from signed identity. The import should retain these authority and presentation rules. See `frontend/src/features/inventory/pages.tsx` (`Management`) and `frontend/src/app/capabilities.ts`.

## Intended interaction and decisions

Add a small import entry point to each existing collection, visible only to authorized administrators. The flow selects a CSV, encoding, explicit delimiter and header choice; presents source record/line numbers and names for review; fixes one target Tenant; then confirms creation. Mark obviously blank names in Preview without changing the value sent to the backend. GLOBAL ADMIN explicitly selects exactly one concrete Tenant per import, even when entering from a Tenant-scoped collection. TENANT ADMIN sees its own Tenant read-only and cannot change it. The UI must never distribute one import across Tenants. A file/settings/Tenant change invalidates the preview; the selected Tenant is fixed for execution.

Attempt rows independently with the existing Create API and `{name, note: null}`. Preserve source row number, raw name, progress, created ID on success, and localized actionable backend error code/status on failure. Empty names and other backend-invalid values fail as individual rows; later rows continue. Do not preemptively reject or merge duplicate names. Do not automatically replay a POST after an uncertain response; retain its row as requiring human review. Keep partial results visible and refresh the relevant collection after successful creates.

**CSV configuration UI reuse:** The accepted Asset importer's encoding, delimiter, header-presence, parse-error and source-row preview controls are inline in `frontend/src/features/inventory/AssetCsvImport.tsx`, not exported as a generic component. Follow its settings interaction and localized terms where applicable; implement the required header choice and explicit delimiter in the Place-local control. Changing a setting invalidates the preview. Do not extract a shared component solely for this import or copy Asset field mapping or historical-state workflow. This UI decision is separate from parser reuse.

**CSV parser decision:** Use a bounded Place-local browser parser for the approved one-column contract, with `TextDecoder` for the supported encodings and a small quoted-field parser. Preserve raw name values, source record/line numbers and malformed-file errors; reject extra columns before any POST. The accepted `AssetCsvParser` remains backend-only and its `parse-preview` route requires GLOBAL ADMIN. A new backend endpoint/extraction would enlarge this feature and still need a separate Tenant-safe authorization design. Its single-column AUTO limitation is expected; do not change it. Do not add a frontend CSV dependency or a general parser framework. See the [reuse audit](../analysis/location-owner-csv-import-reuse-audit.md).

**Authorized implementation boundary:** Add `frontend/src/features/inventory/PlaceCsvImport.tsx` and a small Place-local parser module beside it; add entry points in `frontend/src/features/inventory/pages.tsx` (`Management`). Update `frontend/src/locales/en.json` and `frontend/src/locales/de.json`; cover parser edge cases with a focused unit test and the role/row flow in `frontend/tests/place-csv-import.spec.ts`, with existing related-collection Create tests guarding manual behavior. No backend service, database migration, OpenAPI change, Asset CSV code or normal Create-form change is expected.
